Reading the numbers

  • The Release build fixed the tree build: 334.7 ms for eckit vs 347.0 ms for scipy at N = 1.1M. The earlier Debug build took about 3 s. Overall eckit is 7.9× faster than with Debug (geometric mean; last column of the table).
  • With few query points (POIs) the tree build dominates, so eckit and the original are at parity: 0.78× the original's time on average.
  • With many query points eckit is slower, and the gap grows with k: at Q = 100k it takes 5.9× the original's time at k = 1 and 16× at k = 36. Against single-threaded scipy the factors are 2.0× and 3.4×.
  • Three causes, roughly in order: the original queries on all cores (8 here, up to 256 on the full node) while eckit queries run on one thread; eckit's k-d tree query is slower per thread than scipy's at large k; and the per-point Python loop. A separate single-thread check (1M points, 100k queries) put eckit's own C++ batch query at 0.49 s (k = 4) and 2.05 s (k = 36), with the Python loop about 25% slower than that.
  • Results agree: neighbour indices identical in at least 99.9998% of queries, distances within 1.2e-07 relative.
